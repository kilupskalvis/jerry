# Settings and lockfile

## settings.yaml

Optional org-level policy at `.jerry/settings.yaml`. Applies to every workflow in the repo.

```yaml
policy:
  deny:
    - "bash(rm -rf:*)"
    - "bash(chmod 777:*)"
    - "read(.env)"
    - "read(**/*.pem)"
    - "write(.env)"
  budget:
    max_cost_per_run: 10.00
  runtimes:
    allowed: [pi]
```

### Fields

| Field | Type | Description |
|---|---|---|
| `policy.deny` | string[] | Non-overridable deny rules merged into every step. Workflows cannot relax these. |
| `policy.budget.max_cost_per_run` | float | Hard ceiling on total run cost. Budget breach = exit 4. |
| `policy.runtimes.allowed` | string[] | Allowlist of runtime names. Validation refuses other runtimes. |

### Enforcement

Settings are enforced at two points:

1. **Authoring time** — `jerry validate` and `jerry generate` refuse specs that violate policy (e.g., a workflow using a disallowed runtime).
2. **Execution time** — `jerry exec` re-checks before invoking the runtime. Defense in depth, since generated YAML can be hand-edited.

### Default deny set

`jerry init` creates a settings.yaml with a default deny set covering common dangerous patterns: destructive shell commands, credential file access, and settings file writes.

## jerry.lock

Pinned runtime versions at `.jerry/jerry.lock`. Generated by `jerry lock`, committed to the repo.

```yaml
version: 1
runtimes:
  pi:
    package: "@mariozechner/pi-coding-agent"
    version: "0.73.1"
```

### Fields

| Field | Type | Description |
|---|---|---|
| `version` | int | Lock format version. Must be `1`. |
| `runtimes.<name>.package` | string | npm package name. |
| `runtimes.<name>.version` | string | Pinned version. |
| `runtimes.<name>.checksum` | string | Optional integrity hash. |

### How it works

- `jerry lock` runs `pi --version` and writes the result to `jerry.lock`.
- The compiler reads `jerry.lock` and emits a pinned `npm install -g <package>@<version>` in the generated CI preamble.
- The pi adapter runs `pi --version` at startup and refuses to proceed if the installed version doesn't match the pin (exit 2).
- An absent lockfile is a validation warning, not an error — local development works without it.

### Why pin

Same reason as Terraform's `.terraform.lock.hcl`: CI should install the exact runtime version you tested against. Version drift between local and CI is a common source of subtle failures.
